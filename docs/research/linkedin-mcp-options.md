# LinkedIn MCP options for `social-automation`

> question: Is there something similar to XActions and Reddit MCP Buddy for LinkedIn that should be imported into `social-automation` before we lock the repository, so we can have broad social coverage without repeating this integration later? Prefer browser automation, but evaluate a strictly interactive model: visible browser, existing user session, one user-requested action at a time, explicit confirmation for writes, low rate, and no background jobs, scheduling, bulk scraping, watch lists, or data warehouse.
> researched: 2026-10-11

## summary

Yes, but no existing project is a complete fit. The strongest base for the requested visible, interactive browser model is [`stickerdaniel/linkedin-mcp-server`](https://github.com/stickerdaniel/linkedin-mcp-server/tree/ad009206c9d8c2bf07d869ea032fc8351fb11770): it is actively released, Apache-2.0 licensed, uses a real browser session, can run with the browser visible, and already covers feeds, post search, profiles, companies, jobs, and messages. It does not expose post-detail, comment-thread, nested-reply, post-creation, reaction, or post-comment tools, so those would still need to be added. ([README: tools and browser session](https://github.com/stickerdaniel/linkedin-mcp-server/blob/ad009206c9d8c2bf07d869ea032fc8351fb11770/README.md#L56-L77), [README: visible browser option](https://github.com/stickerdaniel/linkedin-mcp-server/blob/ad009206c9d8c2bf07d869ea032fc8351fb11770/README.md#L151-L159), [v4.27.0 release](https://github.com/stickerdaniel/linkedin-mcp-server/releases/tag/v4.27.0), [license](https://github.com/stickerdaniel/linkedin-mcp-server/blob/ad009206c9d8c2bf07d869ea032fc8351fb11770/LICENSE))

The closest safety architecture is [`devag7/linkedin-mcp`](https://github.com/devag7/linkedin-mcp/tree/4b9e81681b3d05ced9148199554b21c53c81d141), whose writes are disabled by default and require a server-issued preview token plus `confirm:true`. It already has post creation, reaction, and comment writes, but it lacks post search and comment/reply reads and makes undocumented Voyager requests from the browser page instead of visibly navigating the UI. ([README: architecture and write gate](https://github.com/devag7/linkedin-mcp/blob/4b9e81681b3d05ced9148199554b21c53c81d141/README.md#L44-L53), [README: tool inventory](https://github.com/devag7/linkedin-mcp/blob/4b9e81681b3d05ced9148199554b21c53c81d141/README.md#L354-L365))

Recommendation: import `stickerdaniel/linkedin-mcp-server` as the LinkedIn subtree, then port the small, useful safety concepts from `devag7/linkedin-mcp` rather than importing two LinkedIn runtimes. This gives the repository one LinkedIn implementation and the broadest read surface while preserving the visible-browser direction. This is a product-fit judgment based on the cited capabilities, not a claim of LinkedIn approval.

The proposed guardrails reduce accidental or high-volume activity but do **not** make browser automation compliant. LinkedIn explicitly prohibits third-party browser automation, scraping, automated access, posting, commenting, liking, sharing, and messaging, and says accounts using such tools risk restriction or shutdown. ([LinkedIn prohibited software and extensions](https://www.linkedin.com/help/linkedin/answer/a1341387), [LinkedIn User Agreement §8.2](https://www.linkedin.com/legal/user-agreement#dos))

## findings

### What LinkedIn officially permits through APIs

The documented Posts API supports creating posts, retrieving a post by URN, batch retrieval, and finding posts by author or sponsored account. The documented author finder is not a general home-feed or keyword-search API. ([LinkedIn Posts API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api?view=li-lms-2026-09))

The documented Social Actions API supports paginated comments on posts, comments on comments, individual and batch comment retrieval, creation of top-level and nested comments, and reactions. It therefore has the primitives required for full reply traversal if the application has the necessary permission. ([LinkedIn Network Update Social Actions API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/network-update-social-actions?view=li-lms-2026-09))

Those read permissions are the constraint. `r_member_social_feed` is restricted to select developers, while organization reads require an authorized Page role; the private compliance permissions are also granted only to select developers. ([LinkedIn Network Update Social Actions API: permissions](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/network-update-social-actions?view=li-lms-2026-09#permissions))

LinkedIn describes Community Management as a vetted product with Development and Standard tiers. Development defaults are 500 requests per app and 100 per member, and LinkedIn currently says `r_member_social` is closed and is not accepting Member Post Management access requests. ([LinkedIn Community Management overview](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/community-management-overview?view=li-lms-2026-09))

The official API is therefore viable for approved organization/Page management and self-serve member writes, but it cannot provide the requested broad personal feed, arbitrary post search, and member comment-thread reading for an ordinary new app. This conclusion follows from the documented endpoints and restricted read permissions above.

### Platform policy and account risk

LinkedIn's current User Agreement forbids software, scripts, robots, crawlers, browser plug-ins, and other technology used to scrape or copy the service. It separately forbids unauthorized automated access and automated contact, messaging, posting, commenting, liking, sharing, or resharing. LinkedIn reserves the right to restrict, suspend, or terminate accounts for violations. ([LinkedIn User Agreement §§3.4 and 8.2](https://www.linkedin.com/legal/user-agreement#dos))

LinkedIn's help center applies that rule directly to third-party crawlers, bots, browser plug-ins, browser extensions, scraping, appearance modification, and activity automation; it says users risk account restriction or shutdown and that prohibited tools may stop working without notice. ([LinkedIn prohibited software and extensions](https://www.linkedin.com/help/linkedin/answer/a1341387))

Consequently, a visible browser, a saved first-party login, one action per prompt, explicit write confirmation, serial execution, low request rates, and the absence of background jobs are worthwhile risk controls, but none changes the compliance conclusion. The controls reduce unintended actions, bursts, retries, and ambiguity; they do not create LinkedIn authorization.

### Recommended import and adaptation boundary

Import `stickerdaniel/linkedin-mcp-server` as a subtree snapshot. Do not import `devag7/linkedin-mcp` as a second runtime; record it as the safety-design reference and reimplement only the needed ideas in the chosen codebase. Both licenses permit modification and redistribution subject to their terms, but the imported Apache-2.0 code must retain its license and notices. ([Apache-2.0 license and NOTICE](https://github.com/stickerdaniel/linkedin-mcp-server/tree/ad009206c9d8c2bf07d869ea032fc8351fb11770))

The minimum LinkedIn slice should be:

1. `linkedin_get_feed` and `linkedin_search_posts`, reusing the selected project's existing browser reads. ([existing tools](https://github.com/stickerdaniel/linkedin-mcp-server/blob/ad009206c9d8c2bf07d869ea032fc8351fb11770/README.md#L75-L76))
2. `linkedin_get_post`, which opens one supplied LinkedIn post URL and returns its text, author, time, media links, engagement counts, and canonical URL.
3. `linkedin_get_comments`, which visibly opens that post, expands “load more comments” and “load previous replies” controls, deduplicates comments, preserves parent/child relationships, and returns an explicit `complete`, `partial`, or `blocked` status. Completion must be bounded by a user-supplied page/interaction limit so “read all replies” never silently becomes an unbounded crawl.
4. User-triggered write tools for post, comment/reply, reaction, message, and connection actions. Every call first returns a preview; a second call must include an operation ID, short-lived preview token, identical target/content hash, and explicit confirmation. The `devag7` protocol is a concrete first-party implementation reference. ([preview and replay protocol](https://github.com/devag7/linkedin-mcp/blob/4b9e81681b3d05ced9148199554b21c53c81d141/README.md#L260-L330))
5. Visible browser by default, serial tool execution, no automatic retry of writes, no scheduler, no background daemon, no periodic monitoring, no bulk account lists, and no persistent post/profile warehouse. The chosen base already supports visible browser mode and serializes tool calls. ([visible mode and serialized calls](https://github.com/stickerdaniel/linkedin-mcp-server/blob/ad009206c9d8c2bf07d869ea032fc8351fb11770/README.md#L151-L209))
6. Immediate stop on login challenge, verification checkpoint, restriction page, or unclear write result. The result should tell Codex to ask the user to inspect LinkedIn manually instead of retrying. The risk-reduction rationale follows `devag7`'s circuit breaker and unknown-outcome behavior, while its own README correctly states that these controls cannot guarantee account safety. ([checkpoint behavior](https://github.com/devag7/linkedin-mcp/blob/4b9e81681b3d05ced9148199554b21c53c81d141/README.md#L217-L256), [unknown outcomes](https://github.com/devag7/linkedin-mcp/blob/4b9e81681b3d05ced9148199554b21c53c81d141/README.md#L278-L306))

This shape closes the functional gap once, but it should be described internally as “interactive LinkedIn browser control,” not as a compliant LinkedIn API integration. LinkedIn's policy source is unambiguous that third-party browser automation remains prohibited. ([LinkedIn prohibited software and extensions](https://www.linkedin.com/help/linkedin/answer/a1341387))
